# cdev

*[English README](README.md)*

`cdev` は明示的に呼び出す Codex のマルチエージェントワークフローで、
コーディングタスクを実装します。ルートエージェントが、継続利用する
producer と独立 reviewer の2エージェントを調整します。

## 呼び出し例

~~~text
$cdev:coding 要求された機能を実装し、リポジトリの検証を実行して、
変更はコミットせずに残してください。
~~~

スコープ、必須の検証、コミットの可否、変更してはいけないファイルなど、
重要な制約は依頼に含めてください。

- `--review-rounds N` は設計・コードの各 producer/reviewer ループ上限です。
  デフォルトは5回、範囲は1〜10回です。
- `--qa-attempts N` は QA/修正ループ上限で、デフォルトは5回、範囲は1〜10回です。
- `--commit` は QA 成功後に今回の変更をコミットします。省略時はコミットしません。
- `--output {dir}` は設計書の出力先ディレクトリです。省略時は
  `.codex/tmp/cdev-coding-{timestamp}-design/` を使います。相対パスは対象リポジトリの
  ルートから解決します。リポジトリのルート、ソースを含むディレクトリ、今回削除する
  作業用ディレクトリ自身やその配下は指定できません。

設計書 `{design_dir}/design.md` は実行後も残り、最終報告にパスを表示します。
作業用の `.codex/tmp/cdev-coding-{timestamp}/` は実行後に削除します。
`--commit` は `.codex/tmp/` と設計書の出力先をステージ対象から除外します。

## ワークフロー

1. リポジトリ指示、タスクスコープ、開始時のクリーンな worktree を確認します。
2. 継続利用する producer と reviewer を1つずつ起動します。
3. チーム分析を行い、設計を作成します。
4. ゲートを通過するまで設計と設計レビューを反復します。
5. 設計を実装し、コメントとコードをレビューして指摘へ対応します。
6. リポジトリ固有の検証と独立 QA ゲートを実行します。
7. ユーザーが明示的に依頼した場合だけコミットします。

後続フェーズでも同じ2つの子エージェントを再開し、文脈を維持しつつ
ルートワークフロー用に1スロットを空けます。スロットが少ない場合は
作業をキューに入れます。

設計の作成・改訂と設計レビューは [発散パターン防止ルール](rules/divergence.md) に従います。
未確定の仕様・不変条件、個別ケースへの対処では閉じきれない問題クラス、裁定されていない
要求の相反、既存設計との不整合を設計段階で扱います。reviewer は該当箇所を Major 以上として
指摘します。設計が明記した受け入れ範囲の外の反例は指摘せず、その範囲ではタスクを
満たせない場合に限り、範囲自体を指摘します。

## 安全性と出力

- ユーザー変更をワークフローの出力と誤認しないよう、開始時にクリーンな
  Git worktree が必要です。この確認では `.codex/tmp/` と明示された `--output` の
  指定先配下を除外するため、過去の設計書は次の実行を妨げません。
- プロジェクトとユーザーの Codex エージェントプロファイルを役割プロンプトに
  利用でき、同梱の参照プロファイルをフォールバックにします。
- 中間ファイルは `.codex/tmp/` 以下だけに出力します。
- 対象リポジトリの `AGENTS.md`、フォーマット、ビルド、テスト指示に従います。

## 必要条件

- Git リポジトリ
- Python 3.11 以降
- Codex のコラボレーションツール
- プロジェクト固有のビルド・テスト依存関係
